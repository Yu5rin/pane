# 観点2「余裕があれば直すもの」対応メモ

担当範囲: `docs/調査記録/点検-機能と動作.md` の「余裕があれば直すもの」(8〜12)。
「今すぐ直すべきもの」(1〜7)はv1.1.2(#17)で対応済みのため対象外。

## 事実確認

着手前にコードを読み直し、指摘が事実かどうかをまず確認した。全件、指摘どおりの実装だった
(誤りは無かった)。

## 対応した項目

### 5(旧8). 更新の入れ替え途中の電源断で復旧不能
- 事実確認: `UpdateService.ApplyUpdate`はexe→distの順にコピーし、`CleanupLeftovers`は
  退避ファイル(`*.pane-old`)の有無だけを見て無条件に削除していた。指摘どおり。
- 直した内容:
  - `Pane/UpdateLeftoverPolicy.cs`(新規): 「退避ファイル・完了マーカーの有無」から
    `DeleteBackups`/`KeepBackups`/`None`を決める純粋な判定クラス。
  - `Pane/UpdateService.cs`: `ApplyUpdate`がexe/distのコピーを最後までやり遂げた直後に
    完了マーカー(`pane-update.ok`)を書く(`WriteCompletionMarker`)。`CleanupLeftovers`は
    このマーカーが無ければ退避ファイルを一切消さず、警告ログだけ残す(自動での戻し入れは
    実行中exeの自己書き換えになり危険なため行わない。手動復旧の材料を残すだけに留めた)。
- テスト: `Pane.Tests/UpdateLeftoverPolicyTests.cs`(6件)。

### 6(旧2の一部再掲・実質9). Shift_JISへ切り替えて保存すると表現できない文字が黙って"?"になる
- 事実確認: `TextFileService.EncodeBody`は既定の置換フォールバックのままで、読み込み側
  (ExceptionFallback)と非対称だった。指摘どおり。
- 直した内容:
  - `Pane/FileEncodingKind.cs`(新規): 既存の`FileEncodingKind`列挙型をTextFileService.csから
    切り出し(EncodingLossGuardがPane.Tests側で単体テストするために必要)。
  - `Pane/EncodingLossGuard.cs`(新規): 指定エンコーディングで表現できない文字が含まれるかを
    `EncoderFallback.ExceptionFallback`で実際に試して判定する純粋クラス。
  - `Pane/MainForm.cs` `HandleSaveRequestCore`(旧HandleSaveRequest): 保存直前にこの判定を通し、
    表現できない文字があれば確認ダイアログ(既定はキャンセル側)を出す。「いいえ」なら保存を
    中止する。
- テスト: `Pane.Tests/EncodingLossGuardTests.cs`(9件。絵文字・ハングル・不正Shift_JISの
  置換文字U+FFFD等)。

### 7(旧3・実質8). 起動済みのときに相対パスを渡すと既存プロセスのCWDで解決される
- 事実確認: `Program.cs`は`initialPath`を相対パスのまま名前付きパイプへ渡していた。指摘どおり。
- 直した内容:
  - `Pane/StartupPathResolver.cs`(新規): 起動引数を「呼び出し時点の作業ディレクトリ」を基準に
    `Path.GetFullPath`する純粋関数(null・例外時はそのまま返す)。
  - `Pane/Program.cs`: 引数のパース直後、多重起動チェックより前に一度だけ絶対パス化する。
- テスト: `Pane.Tests/StartupPathResolverTests.cs`(5件。作業ディレクトリを切り替えながら確認)。

### 8(旧4・実質9). タブを「閉じる」で破棄してもスナップショットが残る
- 事実確認: `HandleTabsChanged`は毎回`_tabInfos`を丸ごと置き換えるだけで、消えたタブの
  自動保存スナップショット(`AutoSaveService`、tabのguidがファイル名)を消す処理が無かった。
  指摘どおり。
- 直した内容:
  - `Pane/TabSnapshotCleanup.cs`(新規): 更新前後のguid一覧を比べ、消えたguid(=閉じられた
    タブ)を列挙する純粋クラス。
  - `Pane/MainForm.cs` `HandleTabsChanged`: `_tabInfos`を置き換える前にこの判定を通し、
    消えたguidの自動保存スナップショットを削除する。
- テスト: `Pane.Tests/TabSnapshotCleanupTests.cs`(6件)。

### 9(旧5). 同じファイルを2ウィンドウで開けて後勝ち上書き
- 事実確認: `PaneApplicationContext.OpenWindow`に既存ウィンドウを検索する処理が無かった。
  指摘どおり。
- **設計判断**: VS Code方式(既に開いているウィンドウ/タブを前面化する)を採用した。
  メモ帳のように無警告で複数開かせて後勝ち上書きを許すより、上書き事故を未然に防げると
  判断した。仕様書に本件の定めは見当たらなかった。
- 直した内容:
  - `Pane/PaneApplicationContext.cs` `OpenWindow`: 新規ウィンドウ・タブを作る前に、
    `_windows`の中に同じパスを開いているウィンドウが無いか(`GetOpenFilePaths()`で
    タブ内も含めて検索)確認し、見つかれば`ActivateTabForPathIfPresent`でそのタブへ
    切り替えたうえで`WindowChrome.ForceActivate`するだけにして戻る。
    recoverFrom(異常終了からの復元)・droppedFile(パス不定のドロップ)は対象外。
  - `Pane/MainForm.cs`: `ActivateTabForPathIfPresent(path)`を追加(タブ形式のとき、該当タブへ
    "activate-tab"メッセージを送る)。
  - `src/main.js`: `"activate-tab"`メッセージを受けて`switchToTab`する処理を追加。
- **スコープの境界(意図的に対象外にしたもの)**: タブ形式(隠し設定)の
  「最近使ったファイル」「サイドバー」「クイックオープン」「グローバル検索」「D&D」は
  `MainForm.OpenInNewTab`を`OpenWindow`を経由せず直接呼ぶため、この重複チェックの対象外の
  ままにした(それぞれ`HandleOpenPathRequestAsync`・`OpenDroppedPathAsync`から直接呼ばれる)。
  レビューの指摘・再現手順がいずれも「エクスプローラーで2回開く」(=`OpenWindow`経由)を
  指しており、タブ形式自体が仕様書に無い隠し設定であるため、影響範囲をそこに絞った。
  拡張する場合は`OpenInNewTab`の先頭に同じ重複チェックを差し込むのが素直だが、
  コンストラクタへ新しいコールバックを増やす必要があり手を広げすぎると判断した。
- テスト: WinForms/Formの実物が要るため単体テスト化はしていない(UI層の判断であり、
  純粋ロジックへの切り出しどころが無い)。`dotnet build`で構文・型は確認済み。実機での
  目視確認が必要(この環境ではWindows実機を動かせない)。

### 10(旧6). 外部での削除・リネームを検知しない
- 事実確認: `FileSystemWatcher`の`NotifyFilter`にDeleted/Renamedの購読が無かった。指摘どおり。
- 直した内容:
  - `Pane/MainForm.cs` `StartWatching`: `NotifyFilter`に`NotifyFilters.FileName`を追加し、
    `_watcher.Deleted` / `_watcher.Renamed`を購読。
  - `OnFileDeletedExternally` / `OnFileRenamedExternally`を追加。既存の
    `OnFileChangedExternally`と同じデバウンス(`_externalChangeDebounceTimer`)に載せる。
  - `OnExternalChangeDebounceElapsed`: 削除・リネームを「変更されました」より優先して扱い、
    OKのみの確認ダイアログで知らせる(自動での追従・復旧は行わない。Ctrl+Sすれば
    従来どおり同じ名前で新規作成される)。
  - 自分自身の保存(`SaveAtomic`の`File.Move(overwrite:true)`)は、移動先の名前が
    Filterと一致するため理論上Renamedの対象になりうるが、`SuppressWatcherDuring`が
    保存中`EnableRaisingEvents`自体をfalseにしており、Changedと同じ理屈で誤検知しない。
- テスト: FileSystemWatcher依存のため単体テスト化していない(既存のChanged系ハンドラも
  同様に未テスト)。実機での目視確認が必要。

## 見送ったもの・小さく対応したもの(11)

- **セッション復元が最後に閉じたウィンドウのみ**: 指示どおり見送った。複数ウィンドウの
  復元へ作り替える話になり、スコープが大きく広がるため着手していない。
- **最大化状態が保存されない**: 小さく対応した。`AppSettings.WindowMaximized`を追加し、
  `PaneApplicationContext`のFormClosing(記録)・OnWindowClosed(永続化)・OpenWindow
  (セッション最初の1枚にだけ復元。カスケード配置と相性が悪いため2枚目以降は対象外)を
  それぞれ直した。`docs/設定項目一覧.md`にもキーを追記した。単体テストは無し(WinForms実物の
  状態遷移のため)。
- **文字数がUTF-16単位**: 見送った。`src/text-stats.js`の変更はステータスバー常時表示の
  挙動を変えるため`.verify-*.mjs`の追加・既存回帰の確認まで含めると手が広がると判断し、
  今回は着手していない。
- **Ctrl+S連打・「更新する」連打のC#側ガード無し**: 小さく対応した。
  - `Pane/MainForm.cs`: `HandleSaveRequest`を進行中フラグ付きの薄いラッパーにし、実体を
    `HandleSaveRequestCore`に分離。保存処理が進行中の間、後続の"save"要求は無視する。
  - `Pane/SettingsBridge.cs`: `HandleApplyUpdateRequestAsync`に`_applyUpdateInProgress`
    フラグを追加し、二重実行を防ぐ。
  - どちらも実害が小さい(壊れはしない)指摘だったため、単体テストは追加していない
    (状態を持つ非同期メソッドで、切り出せる純粋ロジックが無い)。
