# 会社のPCでウィンドウを開くたびに2秒待たされていたのは、SmartScreenだった

対応した版: v1.1.8

会社のPCが全体に遅かった。バンドル評価が2092〜2911ms（自宅は73〜122ms）、
2枚目のウィンドウ表示が3038ms（目標300ms）、設定画面の下準備が8476ms。
起動が6秒を超えて「フォールバックで強制表示」になった回もあった。

原因は**WebView2のSmartScreen（URLの評判チェック）**だった。Paneでも、JSでも、
ファイル読み取りでも、CPUでもなかった。

## 外した仮説を先に書く

この調査では**3回続けて外している**。順に書く。どれも「もっともらしいが、確かめて
いなかった」もので、確かめる前に手を打っていたら3回とも無駄な変更になっていた。

### 1回目「ウイルス対策がファイルを検査しているから遅い」

会社のPCで dist（413件20MB）を読むと、1回目20,086ms・2回目56ms・3回目45ms。
初回だけ400倍遅い。Defenderの初回スキャンは実在した。

**しかし Pane が起動時に読む14件で測り直すと、1回目2493ms・2回目以降10〜14ms。**
Paneを起動して閉じたあとも12〜14ms。ログでは同じ日に何度起動してもバンドル評価は
2秒のままで、一度も速くなっていない。初回スキャンでは説明がつかなかった。

このとき「ファイルを14件から1件にまとめれば90%短縮する」と見立てていた。
**打たなくてよかった手**だった。

### 2回目「取得が47倍遅い」——計測の読み違い

ログの `最後の完了=2069ms` を「取得に2069msかかった」と読んでいた。正しくは
`responseEnd` の最大値、つまり**「起動開始から2069msの時点で最後の取得が終わった」
という時刻**で、その中にはHTML取得もJSの実行も全部入っている。

しかも同じ計測には「100ms以上かかったファイルがあれば名前を出す」仕組みが入っていて、
会社のログにその行は**一度も出ていなかった**。どのファイルも100ms未満だった、という
決定的な手がかりが、出ていないという形でそこにあった。

### 3回目「V8のコンパイルがコア数の差で遅い」

会社は4コア（i5-1145G7）、自宅は14コア（i5-14500）。CPU単体でも2.1倍差
（平方根200万回で3982ms 対 1865ms）。JSは1.4MBある。コンパイルは別スレッドで走るので
メインスレッドの計測には出ない——筋は通っていた。

**トレースを見ると `v8.compileModule` は12件で37ms、`v8.evaluateModule` は25ms。**
外れ。

## 実際に起きていたこと

DevToolsのPerformanceトレース（会社実機、2026-09-10）を読んで確定した。

```
   4.8ms    NavigationRequest::WillProcessResponse 開始
   5.0ms    SmartScreenNavThrottle が保留を返す      ← ここで審査の列が止まる
2005.6ms    Resume。残りのスロットルが一斉に動きだす
2005.6ms    CommitNavigation
2008.1ms    index.html のリクエスト送信
2059.2ms    最後のチャンクまで取得完了               ← ページの読み込みは51ms
2094.2ms    DOMContentLoaded
```

ナビゲーションの審査はスロットルの列になっていて、`SmartScreenNavThrottle` が
5.0msで保留を返したまま2秒戻ってこない。

その2秒間、**誰も働いていない**。

| | |
|---|---|
| 15.5秒の記録のうちCPU作業 | 324ms（Scripting 75ms・Rendering 50ms・System 161ms・他） |
| 2秒間で最長のタスク | 1.8ms |
| 16ファイルの取得 | 合計3ms（15件はメモリキャッシュで0ms） |
| index.html の Timing | Stalled 1.71ms、Content Download 0µs |
| GpuVSyncThread 1796ms | 1件15.9ms＝ちょうど1フレーム。働いた証拠ではなく暇だった証拠 |

SmartScreenは「このURLは安全か」をマイクロソフトのサーバーへ問い合わせる。会社の
ネットワークからはそこへ届かず、毎回タイムアウトの2秒を使い切っていた。届かないので
結果もキャッシュされず、何度起動しても毎回2秒。自宅では即答が返るため一度も
表面化しなかった。

説明できていなかったものが、これで全部つながる。

- ウィンドウを開くたびに2秒（ウィンドウごとにナビゲーションが起きる）
- 2枚目のウィンドウ表示3038ms
- 何度起動しても速くならない（毎回タイムアウトする）
- 自宅では起きない

## 直したこと

`CoreWebView2Settings.IsReputationCheckingRequired = false`。

Paneのウィンドウが読むのは `https://pane.local/` ただ1つで、中身は自分のPCの
distフォルダ。外部サイトはWebView2では開かず、OSの既定ブラウザへ渡している
（`ExternalLinkService`）。評判を問い合わせる相手がそもそもいないので、切っても
守られる範囲は変わらない。

### 3つのウィンドウすべてで呼ぶ必要がある

公式ドキュメントより:

> SmartScreen is enabled or disabled for all CoreWebView2s using the same user data
> folder. **If IsReputationCheckingRequired is true for any CoreWebView2 using the
> same user data folder, then SmartScreen is enabled.**

**1つでも設定を漏らすと、そのウィンドウが動き出した時点で全体が有効に戻る。**
PaneのWebView2は本文・設定・取扱説明書の3つある。

これは「繰り返し出てきた誤り」8番（入口が複数あるものを、入口ごとに塞ごうとする）と
まったく同じ形で、既に2回やっている。対象がWindows専用APIでテストから直接呼べないため、
**ソースを走査して呼び忘れを捕まえるテスト**を書いた
（`Pane.Tests/WebViewReputationCheckTests.cs`）。`EnsureCoreWebView2Async` を呼ぶ
ファイルは、必ず `WebViewReputationCheck.Disable` も呼んでいること。4つ目のウィンドウが
増えたら落ちる。

テストが実際に漏れを捕まえることは、`HelpWindow.cs` から1行消して落ちること、
戻して通ることを確かめてある。

## 別件として残ったもの

- **会社のdistが413件20MB、自宅は208件8.64MB。** 同じ版なのに倍ある。手動でZipを
  上書き展開したとき、古いチャンクが消えずに残ったもの。自動更新は dist を丸ごと
  置き換えるので起きない（`UpdateService.ApplyAsync`）。取扱説明書の手動更新の
  手順に「distフォルダを消してから展開する」を書き足すべき
- **CPUは2.1倍遅い。** これは事実で、JSの評価時間の差（会社50〜119ms 対 自宅35ms）は
  これで説明がつく。ただし体感の2秒とは桁が違う

## 繰り返さないために

- **「もっともらしい」で手を打たない。** この件では3回続けて外した。1回目の見立て
  （ファイルをまとめる）で手を打っていたら、効かないうえに遅延読み込みを壊していた
- **出ていないログも手がかり。** 「100ms以上かかったファイルがあれば名前を出す」が
  一度も出ていなかったことが、取得は速いという証拠だった
- **アイドルが96%なら、犯人はコードの中にいない。** CPUが働いていないのに時間が
  過ぎているなら、探すのは外側（待っている相手）であって、コードの重い部分ではない
