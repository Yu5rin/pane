# 実機ログで見つかった足止め（5件）

対応した版: 次の版

2026-09-05の実機ログを読んで見つけたもの。手元（Linuxコンテナ）では
どれも再現しない。**実機のログを実際に読むまで、5件とも誰も気づいていなかった。**

## 前提として間違えていたこと

この調査の前まで、「起動時間の8割はJSのバンドル評価で約2.2秒」という数字を
前提に説明していた。実機ログを読むと**73〜122ms**だった。過去の版で測った数字を、
現在のものとして長く扱っていた。

実機の数字を持たないまま性能の話をしない。

---

## 1. ファイルを開くたびに15秒待たされる

**ログに出ていたこと**

```
更新直後の起動: 同じ場所の古いPane(PID=xxxx)がまだ動いているので終了を待つ
```

これがファイルを開くたびに出て、そのつど15秒（`WaitForPreviousProcessExit`の上限）
待たされていた。その間ウィンドウは出ない。

**なぜ起きたか**

`UpdateService.WaitForPreviousProcessExitAfterUpdate()` は、退避ファイルが残っている間
（更新から5分以内）、「同じフォルダで動いている自分以外のPane.exe」を**無条件に**
「入れ替えられた古いプロセス」とみなしていた。

見落としていたのは、この判定がMutex（多重起動の確認）より**前**に走ることである。
Paneはファイルを開くたびに新しいプロセスが起動し、常駐プロセスへ引き渡して即終了する。
つまり更新から5分のあいだに2枚目を開くと、相手は「古いプロセス」ではなく
**たった今も働いている現役の常駐プロセス**である。それを毎回15秒待っていた。

**どう直したか**

入れ替えが起きた時刻（退避ファイルの時刻）より**前**から動いているプロセスだけを
古いとみなす（`UpdateProcessWaitPolicy`）。境界は「待たない」側へ倒した。
誤って待つ害（毎回15秒＋次項の前面化失敗）のほうが、誤って待たない害
（更新直後の1回だけ）より実機で重いため。

## 2. 既存ウィンドウへの切り替えで前面化に失敗する

1の副作用。当初は「`SingleInstance`が送るPIDを取り違えている」と見立てたが、
これは外れだった。PID自体は正しく `Environment.ProcessId` を送っていた。

真因は、`AllowSetForegroundWindow` によるフォアグラウンドの委譲権が
**時間で失効する**こと。1の15秒待ちのあいだに権利が切れ、そのあと前面化を
頼んでも効かなくなっていた。1を直せば待ち時間そのものが無くなるため解消する。

見立てを立てたら、それが当たっているかをログで確かめること。半分当たっていると
かえって危ない。

## 3. 更新の完了マーカーの誤検知で警告が出続ける

```
更新: 前回の入れ替えが完了しないまま終了した形跡があるため、退避ファイル(*.pane-old)は削除せずに残す
```

完了マーカー（`pane-update.ok`）はv1.1.4で入れた仕組みなので、**それより前の版で
更新した環境には「退避ファイルはあるがマーカーは無い」が最初から存在する**。
これを一律に「入れ替えが途中で終わった」と扱うと、実際には正常に更新できているのに
起動のたびに警告が出続け、しかも消えない。

新しい安全策を入れるときは、それ以前の版から上がってくる環境がどう見えるかを
必ず考える。

**どう直したか**

マーカーが無い場合でも、次の2つが揃えば「完了していた」と判断して消す
（`UpdateLeftoverPolicy.Action.DeleteStaleBackups`）。

- 退避ファイルが置かれてから24時間以上経っている（入れ替えは数十秒で終わる）
- いま動いているexeが、その退避より後に置かれている

片方だけでは足りない。前者だけだと、入れ替えに失敗したまま1日放置した環境の
**唯一の復旧材料**を消してしまう。

## 4. ファイルを開くたびにダウンロードフォルダ（約1万件）を走査する

```
FolderService.ScanAsync: ..., 件数=xxxx, 791ms
```

791〜1169msが、同じフォルダの中のファイルを開くたびに繰り返されていた。

**採らなかった案**: 「サイドバーが閉じていれば走査しない」。
`folder-loaded` の結果は Ctrl+P のクイックオープンでも使うため、
サイドバーの表示状態では判断できない。

**どう直したか**

プロセス内で走査結果を2分間だけ使い回す（`TimedCache`）。使い回すのは
**ファイルを開いた副作用としての親フォルダ自動読み込みだけ**に限った。
ユーザーが明示的にフォルダを開いた場合・Pane自身がファイルを作成/削除/改名した
あとの再走査・設定変更後の再走査では、従来どおり必ず走査し直す。

引き換えに、Pane の外でファイルが増減した場合、最大2分は古い一覧が出うる。
キャッシュのキーには走査条件（パス・隠しファイル表示・除外パターン）をすべて含めて
あるので、設定を変えた場合は別のキーになり古い結果は返らない。

## 5. 設定ウィンドウの初回表示に8.5秒

`SettingsBridge.PostSettingsSnapshot` はUIスレッド上で応答を同期的に組み立てるが、
その中に重いものが2つある。

- `FontService`: 全フォントの列挙と、ファミリごとの等幅判定（1つずつ幅を実測する）
- `DetectPandocAvailable`: 外部プロセスの起動（最大3秒待ち）

どちらもプロセス内で一度計算すれば以後は使い回されるため「初回だけ」遅い。

**裏付け**: 同じログで、HelpWindowの事前生成タイマー（本来22.6秒発火）と
起動時の更新確認タイマー（本来25.1秒）が揃って30.0秒台までずれ込み、
設定画面の描画完了直後に一斉に発火していた。UIスレッドがその間ふさがっていた証拠。

**どう直したか**

まだ誰も待っていない起動直後のうちに、バックグラウンドで済ませておく
（`Program.WarmUpForSettingsWindow`）。あわせて `DetectPandocAvailable` に
排他を入れ、事前準備とUIスレッドからの呼び出しが重なっても外部プロセスの起動が
二重に走らないようにした。

**完全には直っていない**。`get-settings` の処理そのものは同期のままなので、
事前準備が間に合わなかった場合（起動直後に設定を開いた場合）は従来どおり待たされる。
非同期化するには送受信の約束を変える必要があり、影響範囲が別件になる。
