# Pane 起動時バンドル調査メモ

調査日: 2026-09-05 (JST)。dist/ は他エージェントが直前にビルドしたもの(2026-09-05 03:03 UTC生成)を
そのまま使用。**製品コードは一切変更していない。**

## 0.0 【あとからの訂正】前提にしていた「2.2秒」は誤り

この調査は「実機の起動時間のうち、JSのバンドル評価が約2.2秒（8割）を占める」という
前提で始めた。その後 2026-09-05 の実機ログを読んだところ、**バンドル評価は73〜122ms**
だった。2.2秒は過去の版で測った数字であり、現在のものではなかった。

したがって以下の「2.2秒に対して-374ms」といった見積もりは**すべて成り立たない**。
削減の余地そのもの（`@codemirror/lang-markdown` が静的importするHTML/CSS/JSの191KB）は
実在するが、削っても得られるのは数十msの一部にすぎず、フォークの手間に見合わない。
**改善は非推奨**という結論は変わらないどころか、より強くなった。

詳しくは [修正-実機ログで見つかった足止め.md](修正-実機ログで見つかった足止め.md) を参照。

## 0. 前提の再確認

- main.js は `<script type="module">` で読み込まれる唯一の静的エントリ(dist/index.html)。
  他の全チャンクは main.js からのESM importで芋づる式に取得される。
- dist/ 全体のJS合計は **8.37MB (201ファイル)**。うち起動時に静的importされる
  クロージャは **12ファイル・約1123KB**。つまり **全体の87%は既にdynamic import化されており、
  起動時には読まれていない**(mermaid本体・mathjax-full各種・katex・legacy-modes言語・
  settings/help別ウィンドウのエントリ等)。過去の「300KB化」作業は的外れではなく、
  むしろ大部分は機能している。問題は残り13%(1123KB)の中身。

### 最大のチャンク chunk-WHBCZIZI.js(401KB)の正体

`@codemirror/view` + `@codemirror/state` + `@codemirror/language` を1つにまとめたもの
(esbuildのcode splittingが、main.js / settings-entry.js / help-entry.js の複数エントリで
共有されるモジュールを1チャンクに集約した結果)。CodeMirrorのコア3パッケージそのものであり、
Mermaid/MathJax/絵文字データ等は一切含まれない。**これはエディタの本体であり、遅延不可。**

## 2. 重要な発見: html/css/js言語パックがmarkdownの依存で強制的に道連れになっている

`src/file-types.js` の `load:` は全言語について正しく `import(...)` (動的import)を
使っており、Pane自身のコードに問題は無い。

しかし `editor.js` が `@codemirror/lang-markdown` から `markdown` を**静的import**しており、
このパッケージ自身が内部で

```
@codemirror/lang-markdown → @codemirror/lang-html → @codemirror/lang-css
                                                   → @codemirror/lang-javascript
```

と静的importの連鎖を持っている(Markdown文書中の生HTML `<script>`/`<style>` を
ハイライトするための埋め込みパーサ)。これはPane側のコードの書き方の問題ではなく、
**`@codemirror/lang-markdown` パッケージ自体の設計**(`node_modules/@codemirror/lang-markdown/dist/index.js`
1行目〜、`node_modules/@codemirror/lang-html/dist/index.js` 1〜3行目で確認)。

この連鎖により、次の**191KB**が「Markdownを開くだけ」で強制的に評価される:
- chunk-OAMPNQOL(lang-javascript) 91KB
- chunk-T2MTCZZ3(lang-html) 35KB
- chunk-GEGGJKQ2(lang-css) 31KB
- chunk-5GC7MZJJ(lezer/lr ランタイム、上記3つが使う) 34KB

**遅延化する方法はほぼ無い**: CodeMirrorの`parseMixed`によるネスト構成は、ネストしたパーサを
**同期的に**返す前提のAPIで、`lang-markdown`の初期化時点でhtml/css/js言語オブジェクトが
即座に必要になる。動的importで後から差し込む形に変えるには`@codemirror/lang-markdown`自体を
フォーク・改造する必要があり、しかもフォークした場合「Markdown内の生HTML/`<script>`/`<style>`の
シンタックスハイライトが起動直後は効かない(非同期ロード完了まで無色)」という体験の劣化を伴う。
費用対効果が悪く、**やるべきではない**という判断を推奨する。

## 3. 既に遅延化されているものの確認(◎正しく動いている)

- **Mermaid**: `src/mermaid-render.js` 14行目、`import("mermaid")` で動的import。
  静的importは無し。起動時クロージャにmermaid関連チャンクは1つも含まれない(確認済み)。
- **MathJax**: `src/math.js` 23〜40行目、mathjax-fullの各サブモジュールを全てPromise.allで
  動的import。同じく静的importなし。AmsConfiguration/MhchemConfiguration/BboxConfiguration
  等の巨大チャンク(dist内に個別ファイルとして存在)は起動時クロージャに含まれない。
- **コード言語パーサ**(python/java/cpp/rust/legacy-modes 多数): `src/file-types.js` の
  `load:` が全て `import(...)`。コードモードでその言語を実際に開いたときだけ読まれる。
  (ただしhtml/css/javascriptの3つだけは上記2の理由で「開かなくても」既に読み込まれている
  ——lang-markdownの副作用であって、file-types.js側の遅延化とは別経路)。
- **設定画面・取扱説明書**: `settings-entry.js`(2KB)・`help-entry.js`(9KB)は別エントリで、
  main.jsの起動クロージャとは独立(dist/settings-window.html, help-window.htmlが個別に読む)。
- **色ピッカーのパネルUI**: `src/editor.js` 4928行目、`import("./color-picker-panel.js")` で
  クリックして開いたときだけ読む。スキャン用の軽量ロジック(色リテラル検出、7.8KB)だけが
  常時ロード。

→ **「遅らせられるはずなのに遅らせていないもの」は実質的に無い。** 唯一の例外(html/css/js言語
パックの強制ロード)は上記2の通りPane側では手を出しにくい。

## 4. 取得(fetch) vs 評価(eval)の実測

### 4.1 方法

`dist/`をローカルHTTPサーバ(ポート8999、`.verify-*.mjs`未使用のポートを選定)で配信し、
Playwright(Chromium)で開いた。`window.chrome.webview`が無いとC#側からの
`apply-settings`/`new-document`メッセージが届かず、main.js自身の起動計測
(`reportStartupMetrics()`、main.js 83〜148行目)が最後まで走らないため、
ダミーのブリッジを注入してその2メッセージだけ模擬送信した(**製品コードは無変更**、
Playwright側からのメッセージ注入のみ)。5回計測。

スクリプト: `/tmp/.../scratchpad/perf-measure.js`(Performance Resource/Navigation Timing)、
`/tmp/.../scratchpad/perf-trace2.js`(CDP Tracingでv8.evaluateModule等を直接計測)。

### 4.2 結果(このLinux環境、ローカルループバック)

main.js自身が出す`[計測:JS]`ログ(5回平均、丸め):

```
HTML取得 ≈ 4ms
バンドル評価 ≈ 79ms   ← 全12チャンク(1123KB)の取得+評価の合計
エディタ生成 ≈ 12ms
UI初期化 ≈ 7ms
起動までに14件取得(最後の完了) ≈ 44ms
```
(「設定反映」「本文反映」の数値はテスト側でメッセージ注入した際のPlaywright↔Chromium間の
IPC往復が混入するため、参考にならない。バンドル評価までの数値は注入の影響を受けない。)

→ この環境では「バンドル評価」79msのうち、**ネットワーク取得が完了する44msまでの区間と、
その後の約35msの純粋な評価待ち**、という大まかな内訳になる(fetch:eval ≈ 56:44)。

さらにCDP Tracingで直接、V8のイベントを見ると:

```
v8.parseOnBackgroundParsing        109ms  ← ダウンロード中にワーカースレッドで並行実行(メインスレッドを塞がない)
v8.evaluateModule                   51ms  ← 実際にメインスレッドを塞ぐ「実行」コスト
V8.CompileCode                      24ms  ← 実行中のJIT
v8.compileModule(各チャンク)     各0.01〜0.05ms  ← ストリーミングコンパイル済みのため確定はほぼ無料
```

**この環境ではV8のスクリプトストリーミングコンパイルにより、パース(構文解析)の大半は
ダウンロードと並行してバックグラウンドスレッドで終わっており、メインスレッドを塞ぐのは
「トップレベルコードの実行」(v8.evaluateModule、51ms)が中心**という結果になった。
1123KBのコードに対して51msは、chromiumの最適化されたエンジンとしては極めて軽い部類。

### 4.3 この環境の比率は実機に持ち込めるか

**持ち込めない、と考えるべき理由が複数ある。**

1. **HTTP取得の性質が違う。** ここでの「取得」はNode.jsの`http`サーバがloopback越しに
   メモリキャッシュ済みファイルを返すだけで、実ディスクI/Oはほぼゼロ。実機は
   WebView2の`SetVirtualHostNameToFolderMapping`経由でNTFS上の実ファイルを読み、
   さらに**ウイルス対策ソフトのリアルタイムスキャン**が絡みうる。
2. **既存コードのコメントに実測の裏付けがある。** `src/main.js` 118〜119行目のコメントに
   「実機では通常68msのところが3255msになっていた」と明記されている。これは
   **同じファイル・同じバイト数**での話であり、CPU実行時間(バイト数に比例するはず)
   ではなく、**I/O側(ディスク/AVスキャン)が原因の異常値**である可能性が非常に高い
   (68ms→3255msは約48倍。CPU実行がバイト数一定のまま48倍に遅くなる理由は無い)。
3. Chromiumのストリーミングコンパイルによる「パースはバックグラウンドで並行」という
   性質はWebView2でも同じエンジン(Chromium)なので**引き継げる**が、それはこの環境で
   評価コストが軽いことの一因でもあり、逆に言うと**バイト数を減らしても評価コストの
   削減効果は割合ほど大きくない**(既にバックグラウンド並行化で大半が隠れているため)。

**結論**: 実機の2.2秒(バンドル評価)の内訳が「取得律速」なのか「評価律速」なのかは、
**この環境の比率からは判断できない**。幸い、**main.js自身が既にこの内訳をログ出力する
コードを持っている**(main.js 120〜137行目、`起動までに${n}件取得(最後の完了=${ms}ms)`
および `遅い順: ...` の行)。これは実機の `%LOCALAPPDATA%\Pane\logs\` に**既に記録されて
いるはず**。次にやるべきは追加の実装や計測ではなく、**その既存ログの当該行を確認すること**
——「バンドル評価=2200ms」に対して「起動までに◯件取得(最後の完了=◯ms)」が
何msになっているかで、取得律速か評価律速かが即座に分かる。

## 5. 改善の見込み(数字)

### ケースA: html/css/js言語パック(191KB)を仮に完全に外せた場合

- 起動時クロージャ: 1123KB → 932KB(-17%)。それでも仕様書の300KB目標には遠く届かない
  (932KBは目標の3倍強)。
- この環境の実測比率(バイト数とevaluateModule時間がほぼ比例すると仮定)で単純換算すると、
  バンドル評価79ms → 約65ms(-14ms程度)。
- 実機の2.2秒に対して**同じ割合で**削減できると仮定した場合(評価律速の場合の話): 
  2200ms × 0.17 ≈ **-374ms**。無視できない額に見える。
- しかし4.3の通り、実機の遅さが**取得律速**(ディスク/AVスキャン)だった場合、バイト数を
  17%減らしても、ファイル**個数**は変わらない(191KBはOAMPNQOL/T2MTCZZ3/GEGGJKQ2/
  5GC7MZJJの4ファイルの中身を減らすだけで、ファイル自体は無くならない——html/css/jsを
  「読み込まない」ようにするには@codemirror/lang-markdownをフォークして依存グラフから
  切る必要があり、単なるコード削減ではなく構造変更になる)ため、取得側の改善効果はほぼ無い。
- しかも実現手段が「上流パッケージのフォーク」であり、2節で述べた通り
  **リスクに見合わないと判断する**。

### ケースB: autocomplete(chunk-76PMPJ3V、49KB)をCompartmentで起動直後ではなく
  「初期表示から1フレーム後」に遅延登録した場合

- 起動時クロージャから49KB(-4.4%)。この環境換算でバンドル評価-3.5ms程度。
- 実装は可能(CodeMirrorのCompartment機構で後からextensionを追加できる)が、
  効果がこの環境ですら数msでしかなく、実機でも大きな改善は見込みにくい。
  かつ「起動直後の一瞬、自動補完が効かない」という体験劣化を伴う。
- **やる意味は薄い。**

### 総合結論

**この調査の結論は「やっても意味が薄い」に近い。** 現在の起動時クロージャ(1123KB)は、
Mermaid/MathJax/コード言語パーサ・別ウィンドウのコードなど**遅延化できるものは既に
遅延化済み**であり、残っているのはCodeMirror本体・Markdown言語・自動補完・自前のUI/
プレビューコードという「エディタが最初のフレームを描くために本質的に必要なもの」が
ほとんど。唯一の例外(html/css/js言語パックの191KB)も、上流パッケージの設計に起因し、
外すには相応のフォークコストとハイライト機能の劣化を伴う。

**数字を追いかける前に、実機の既存ログ(main.js 120〜137行目が出力する
「起動までに◯件取得」の行)を確認し、2.2秒の内訳が取得律速か評価律速かを先に
確定させることを強く推奨する。** それが分からない状態でコードサイズだけを削っても、
削減が効く保証が無い。

## 6. 仕様書8.4節「300KB以内」の扱いについて(意見)

現状、`@codemirror/view`+`state`+`language`(401KB)だけで既に300KBの目標を超える。
Markdown編集機能を持つエディタとして、これらとlang-markdown(61KB)・autocomplete
(49KB)は代替が無い基礎機能であり、**「300KB」は最初からCodeMirror系エディタの
構成では達成不可能な数値だったと考えられる**(過去の「300KB以内にする」完了判定は、
main.js単体(302KB)だけを見て「300KB近辺だから概ね達成」と誤認した可能性が高い
——実際には静的importで芋づるに読まれる11個の追加チャンクがあり、そちらを合算すると
1123KBになる)。

**意見: 数値目標を実態に合わせて改める方を推奨する。** 具体的には
「CodeMirror本体・既定言語(Markdown)・自動補完・自前UIを含む初期ロードJS」を
実測ベースで再定義し(現状1123KB前後)、そのうえで「今後増やさない」ための上限として
再設定するのが妥当。「300KB」のまま据え置いて未達成のフラグを立て続けるより、
実態に基づいた閾値の方が今後の回帰検知(ビルドサイズが知らないうちに増える)に実用的。
達成を目指す場合は、html/css/js言語パックの除去(lang-markdownフォーク)以外に
現実的な手段が無く、費用対効果が悪いため推奨しない。

## 7. 作業量の見積もり(仮にケースAをやる場合。非推奨だが参考値)

- `@codemirror/lang-markdown`相当のコピー版をvendor化 or フォークし、html/css/js
  部分だけ動的import化する改造(推定150〜300行の新規コード、上流の`parseMixed`
  ネスト設定の書き換え含む)。
- `scripts/build.js`のesbuild設定にalias/inject追加(数行〜数十行)。
- `src/editor.js`のimport元差し替え(数行)。
- 生HTML/`<script>`/`<style>`のシンタックスハイライトの回帰テスト追加・既存回帰
  スイート(`.verify-*.mjs`)への影響確認。
- 上流バージョンアップ追従のたびにフォーク差分の再適用が必要になる(継続コスト)。

見送りを推奨するため、この作業自体は着手しない。
