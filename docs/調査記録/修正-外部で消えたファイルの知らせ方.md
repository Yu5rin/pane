# 外部で削除・リネームされたときの知らせ方を、割り込みから保存前の確認へ移した

## きっかけ

利用者が実機で、次のダイアログに出くわした。

```
このファイルは外部で削除されました。
このまま保存すると、同じ名前で新しく作成されます。
                                        [ OK ]
```

開いていたのは `G10010H07.TXT`、本文は0文字。機械が付けたような名前で、
別のツールが作って後始末したファイルだと思われる。
「この通知って要りますか?」という問いから始まった。

## 利用者からの2つの問い

### 「これが一般的な動きではないですか?」

情報としては普通だが、**OKだけのモーダルは一般的ではない**。

- VS Code: タブのファイル名に取り消し線が入るだけで、割り込まない
- Notepad++: ダイアログを出すが「エディタに残しますか?」のはい/いいえで、実際に選ばせる

割り込む側も「選ばせるから割り込む」形になっている。OKしか無いダイアログは、
定義上、判断を求めていない。

### 「開いているのに、消されたり名前を変えられたりするのか?」

**する。** Windowsがファイルの削除を止めるのは、プロセスがハンドルを開いたままに
している間だけである。Paneは読み込み時に `File.ReadAllBytes`（`Pane/TextFileService.cs`）で
読んで即座に閉じており、編集中にファイルを掴んでいない。だからエクスプローラは
何も言わずに削除・リネームする。

これはテキストエディタとして普通の作りで、掴んだままにすると他のツールがそのファイルに
触れなくなる。WordやExcelが「使用中です」と言えるのは、逆に掴んでいるからである。
そして実際に起きた（上のスクリーンショットの件）。

## どう直したか

検知した瞬間の通知をやめ、**上書き保存しようとした時にだけ**確認する。

| | 以前 | いま |
|---|---|---|
| 検知した瞬間 | OKだけのダイアログ | 何も出さない（ログに1行だけ残す） |
| 上書き保存の直前 | 何も確認しない | 保存先が無ければ確認する（はい/いいえ） |
| 名前を付けて保存 | ― | 何も確認しない（利用者が保存先を選んでいるため） |

以前の形の問題は3つあった。

1. 押す以外に選びようがない（＝判断が要らない）ものを、書いている最中に割り込ませる
2. 前面を奪うのでキー入力を飲み込む（Enter/Spaceが「OK」に吸われる）
3. OKを押せば消えるので、後から「まだ無いのか」を確かめる手立てが残らない

## 判定を「監視の検知結果」から「保存する時点で在るか」へ変えた

これが今回いちばん効いている変更である。以前は
「FileSystemWatcherが削除イベントを受け取ったか」というフラグで状態を持っていた。
フラグは取りこぼすし、逆に古くなる。

- 取りこぼす: 監視を張れていない（ログディレクトリ配下は意図的に張らない・監視の例外・
  フォルダごと消された）と、そもそもイベントが来ない
- 古くなる: 消された後で同じ名前のファイルが作り直されたら、フラグはもう嘘になる

いまは保存の直前に `File.Exists` で実際に見る。監視は「名前の変更先がどこか」を
覚えておくためだけに使い、その変更先も、保存時に実在するか確かめてから文面に出す
（名前を変えた後さらに消された場合に、もう無い名前を案内しないため）。

判定と文面は `Pane/ExternalFileStateLogic.cs` へ切り出し、`Pane.Tests` で固定した。
ファイルシステムにもWindows専用のAPIにも触れないので、Linuxでも回る。

## 直さなかったこと

名前を変更されていた場合に「変更後の名前の方へ保存する」という選択肢は用意していない。
確認の文面には変更後の名前を出すので、そちらへ保存したければ「いいえ」を選んでから
「名前を付けて保存」で選べる。3つ目の選択肢を足すかどうかは、実際に困ってから決める。

## 繰り返し出てきた誤りとの関係

「OKだけのモーダル」は、24（下記）の形そのものだった。知らせたい事実はあったが、
それを届ける先として、利用者がいちばん邪魔される場所を選んでいた。
