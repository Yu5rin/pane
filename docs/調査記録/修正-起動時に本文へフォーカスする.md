# 起動したら本文の先頭にカーソルを置く — その過程で出てきた2件の不具合

## 対象

利用者要望「起動したらテキストエリアの一番先頭が選択されているようにして」の実装
（`src/main.js` の `focusEditorAtStart`）と、それによって表面化した2件の不具合。

## 直したかったこと

起動直後のフォーカスは `body` にあり（実測: `view.hasFocus` が false、
`document.activeElement` が `BODY`）、一度本文をクリックするまでキー入力も
Ctrl+Z などのショートカットも効かなかった。CodeMirror のキーマップは
`contentDOM` にフォーカスがある間だけ働くためである。

## どう直したか

`focusEditorAtStart()` で、カーソルを0へ置いてから本文にフォーカスする。
呼ぶ場所は2か所ある。

- スクリプト読み込み直後。C#と繋がっていない状態（ブラウザ単体・回帰スイート）でも必ず通る。
- `trySignalInitialRenderReady()` の中。C#は `initial-render-ready` を受け取るまで
  WebView2を非表示にしているため、非表示のコントロールへのフォーカス指定が実機で
  効かない場合に備えて、表示される直前にもう一度当てる。

どちらも「既に別の場所へフォーカスがあれば奪わない」ので、2回通っても二重には動かない。
カーソルを0にしているのは、前回のカーソル位置を復元する仕組みがまだ無いため
（タブのスナップショットはスクロール位置だけを持つ）。将来それを入れるときは、
ここが復元後の位置を上書きしないよう直すこと。

## 表面化した不具合①: ステータスバーの「外部リソースを読み込む」が取り残される

カーソルのある行は記法をむき出しで見せる（`cursorInside`）ため、フォーカスの有無で
ライブプレビューが組み直され、画像ウィジェット——つまり「ブロック中の外部リソースが
あるか」——も変わる。ところが `updateRemoteBlockedStatus()` は `onSelectionChange`
からしか呼んでおらず、フォーカスが出入りしただけでは選択が動かないため、
表示が古いままになっていた。

起動時にフォーカスするまでは、起動直後は常にフォーカスが無く最初から装飾済みだったので
出番が無かった。`onFocus` / `onBlur` からも呼ぶようにして直した。

## 表面化した不具合②: 打った文字が別の行に紛れ込む（データが壊れる）

こちらが重い。`.verify-blockfield-recompute.mjs` の `(3-toc)` が捕らえた。

### 症状

本文が `cursor-park\n\n` の状態で末尾に `[toc]` と1文字ずつ打つと、最後の `]` が
別の行へ入り、本文が `cursor-park\n]\n[toc]` になる。`[toc]` 行が直前の行と
地続きの段落になるため、目次としても認識されなくなる。

高頻度で状態を記録して、壊れる直前の様子を捉えた。

```
874 doc="cursor-park\n\n"        head=0  focus=true toc=0
912 doc="cursor-park\n\n"        head=13 focus=true toc=0
929 doc="cursor-park\n\n[t]"     head=15 focus=true toc=0   ← 自動で閉じ括弧が入る
951 doc="cursor-park\n\n[toc]"   head=17 focus=true toc=1   ← カーソルの真下で目次が描画された
961 doc="cursor-park\n]\n[toc]"  head=13 focus=true toc=0   ← 次の1文字が押し出された位置へ入る
```

### 原因

`view.setState()` は state を丸ごと作り直すため、フォーカス状態を保持している
`focusField` が新しい state の `create()` の既定値 false に戻る。一方で DOM 側の
フォーカスは何も変わらないので `EditorView.focusChangeEffect` は発火せず、
**実際には本文にフォーカスがあるのに `focusField` は false** という食い違いが、
利用者がいったん別の場所をクリックして本文へ戻るまで残り続ける。

`focusField` を見ているのは表・`[toc]`・Mermaid・コードブロック内数式・`$$`裸記法・
生HTMLの6つのブロック装飾で、いずれも「フォーカスがあってカーソルがそのブロックに
重なっているなら装飾せず生テキストで見せる」という判定に使っている。false のままだと
カーソルの真下でブロックが描画され、カーソルは置き換え範囲（atomic）の外へ押し出される。
そこで次の1文字を打つと、押し出された位置へ入ってしまう。

切り分けでは、`focusField` に相当する値が `state.values` の中で実際に false に
なっていることまで確認した（`buildTocDeco` に一時的な出力を入れて
`{"focused":false,"from":17,"to":17,"paras":[{"from":13,"to":18}]}` を得た）。
`view.hasFocus` は一貫して true だったので、ここだけを見ていると気づけない。

### どう直したか

`view.setState()` の直後に、state の外にある唯一の真実である `view.hasFocus` から
`focusField` を当て直す（`src/editor.js` の `syncFocusFieldToDom`）。
`setState()` の呼び出しは2か所あり、両方に入れた。

- `setValue`（新規文書・別ファイルを開く・ドラッグ&ドロップ）
- `setEditorState`（タブ切替）

### 直す前から存在していた

起動時フォーカスで表面化しただけで、原因は `setState` 側にある。タブ切替
（`setEditorState`）も同じ経路なので、キーボードでタブを切り替えて続けて入力すれば、
この変更より前から壊れた可能性があった。回帰テスト（`.verify-menubar-icons.mjs` の
(H)）は両方の経路を見ており、修正を外すと4件とも落ちることを確認した。

## 直さなかったこと

起動直後はカーソルが1行目にあるため、1行目に記法（`# 見出し` など）があると
その行だけ記法がむき出しで見える。これは `cursorInside` の既定の挙動どおりで、
クリックして1行目に入ったときと同じ見え方になる。利用者に確認し、このまま進めた。
