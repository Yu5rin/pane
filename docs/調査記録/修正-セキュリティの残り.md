## 1. SHA256検証の限界・digest無しの扱い

### 裏取り

- `Pane/UpdateService.cs` FindZipAsset (`digest`取得): 指摘どおり、Zip本体と同じGitHub API
  レスポンス(`assets[].digest`)からハッシュを取っている。Zip本体のダウンロードURLも同じ
  レスポンスの`browser_download_url`。同一の配布元・同一の応答から両方取っているため、
  配布元(GitHubのリポジトリ/アカウント)が乗っ取られてZipが差し替えられれば、digestも
  差し替え後の値が返るので照合は必ず通る。防げるのは転送中の破損程度で、改竄は防げない。
  指摘は事実。
- **文書の食い違いは指摘と少し違った**: 実際にSHA256に言及していたのは`README.md`だけ
  だった(50行目・84行目)。`docs/取扱説明書.md`は元々SHA256/照合/検証/ハッシュのいずれの
  語も含んでおらず(grep 0件)、「取扱説明書もSHA256で照合すると書いている」という前提は
  事実ではなかった。今回、README側の文言を実態に合わせて直すとともに、より詳しく読む
  利用者向けに取扱説明書「外部通信について」の節にも保証範囲の説明を新規に追加した
  (元々書いていなかったものを書き足す形)。

### 直した内容(文書)

- `README.md:50`: 「ダウンロードしたZipはSHA256で照合します」→「照合します。ただしこの
  ハッシュ値もZip本体と同じGitHubから取得しているため、転送中の破損は検出できますが、
  配布元やGitHubアカウントが乗っ取られて中身が差し替えられた場合までは防げません」に修正。
- `docs/取扱説明書.md`(「外部通信について」節、更新の説明の末尾): 同内容の段落を新規追加。
  「保証できるのはダウンロード中に壊れていないことまで」「ハッシュ値も一緒に差し替え
  られるため検出できない」「コード署名による検証は行っていない」の3点を明記した。
- `Pane/UpdateService.cs VerifyHash`のXMLコメントに、同じ限界を明記(`docs/調査記録/点検-セキュリティ.md`
  C-2参照付き)。

### digest無し時の扱い: **実装せず、提案に留めた**

判断: 自動更新を止めて手動更新(リリースページを開く)へ誘導する変更は**実装しなかった**。
指示にある「判断に迷ったら実装せず提案として報告する」に従った。

理由:
- この変更は「今まで自動で入れ替えられていたケースが、digestが無いというだけで入れ替え
  られなくなる」という、更新できなくなる方向の副作用を持つ。digestが実際にいつ空になるか
  (GitHubのdigest機能が付く前の古いリリース、updateCheckUrlを差し替えた別配布元、GitHub側の
  一時的な欠落など)を、Windows実機はもちろんGitHub側の挙動としても私の側で確認する手段が
  無く、「めったに起きない」と請け合えない。
- 一方で影響は「利用者は自動更新できず、手動でダウンロードして差し替える一手間が増える」
  という程度で、セキュリティ上悪化する変更ではない(現状維持)。つまり実装しないことによる
  悪化は無く、実装した場合の悪化(想定外に自動更新が効かなくなる利用者が出る)のほうが
  可逆性に乏しいと判断した。
- 加えて、この判断は仕様書のU-03(SHA256検証)やU-04(手動更新への案内)の設計そのものに
  関わる変更であり、CLAUDE.md「実装フェーズの順序を守る」「仕様書にない機能を推測で追加
  しない」の観点からも、実装フェーズを担当する場で改めて判断されるべきと考えた。

代わりに実装した最小限の対応: digestが無いまま照合を省いて続行する分岐のログレベルを
`Logger.Write`(Info)から`Logger.Warn`に上げた(`Pane/UpdateService.cs VerifyHash`)。
自動更新そのものの可否は変えていないが、「無保証のまま展開が進んだ」ことが既定ログの
`[警告]`で追えるようにした(挙動を変える提案とは別に、observabilityの改善として害が無いと
判断し実装した)。

### 提案(実装していない)

- digestが空のときは自動更新を中止し、「リリースページを開く」(手動更新)へ誘導する
  メッセージを返す。
- 長期的には、ハッシュを別経路(別ホスト、または署名鍵をアプリに埋め込んでの検証)から
  取得する設計へ変更する。

## 2. NavigationStartingの保険が無い件

### 裏取り

`grep -n "NavigationStarting"`が本体・設定・取扱説明書の3ウィンドウのいずれのソースにも
ヒットしないことを確認した。指摘は事実。既存の防御(NewWindowRequestedへの集約、
target="_blank"強制、iframeのsandbox="")は同一タブでのトップレベル遷移そのものを
止めるものではなく、指摘どおり「保険が1行もない」状態だった。

### 直した内容

- 新規 `Pane/NavigationGuard.cs`(`internal static class NavigationGuard`)を追加。
  `IsAllowedTopLevelNavigation(uri, allowedHost)`が、`https://<allowedHost>/...`への
  遷移だけをtrueにする(スキーム比較+ホスト名の大文字小文字を無視した完全一致。
  部分一致で「pane.local.evil.com」のような紛らわしいホストを通さないことをテストで確認)。
  WebView2の型(CoreWebView2NavigationStartingEventArgs等)に依存させず、Uri文字列と
  ホスト名だけを受け取る純粋な判定にすることで、Pane.Tests(net8.0非Windows)へ
  ソースごと取り込める設計にした(ExternalToolLocator/PrivacyLogFormatterと同じ流儀)。
  ※ 既存の`ExternalLinkService.cs`は`using Microsoft.Web.WebView2.Core;`を含み
  Pane.Testsに取り込めない構成のため、あえてそこへは追加せず新規ファイルに分離した。
- `Pane/MainForm.cs`・`Pane/SettingsWindow.cs`・`Pane/HelpWindow.cs`の各`InitializeAsync`
  (WebView2初期化、`Navigate`呼び出しの前)に`CoreWebView2.NavigationStarting`を追加。
  `NavigationGuard.IsAllowedTopLevelNavigation(e.Uri, VirtualHostName)`がfalseなら
  `e.Cancel = true`にして中止し、ログ(既定・URLはホスト名までに短縮、
  `PrivacyLogFormatter.ShortenUri`を利用)に残す。

### 追加したテスト

`<Compile Include>`に`../Pane/NavigationGuard.cs`を追加。

- httpsではないスキーム(http/file/javascript)は拒否する
- about:blankのような特殊URIも拒否する
- 絶対URIとして解析できない文字列は拒否する
- null/空文字は拒否する
- "pane.local.evil.com"/"notpane.local"のような部分一致だけの紛らわしいホストは拒否する

## 4. CopyDirectoryのstring.Replace

### 裏取り

`Pane/UpdateService.cs CopyDirectory`(修正前)は`dir.Replace(source, destination)`で
コピー先パスを組み立てていた。`source`という文字列がパスの途中にもう一度現れる配置
(例: source配下に同名のフォルダがある入れ子)では、意図しない箇所まで置換されうる。
指摘は事実(現状はsource/destinationともPaneが作るGUID付き一時フォルダ名のため
実際に踏む可能性は低いが、堅牢性の問題として妥当)。

### 直した内容

`Path.GetRelativePath(source, dir/file)`でsourceからの相対パスを求めてから
`Path.Combine(destination, 相対パス)`で組み立てる形に変更した(`Pane/UpdateService.cs`
CopyDirectory、920行目付近)。挙動(コピーする内容)自体は変えていない。

このメソッドは実ファイルシステムに触れるI/O処理であり、既存の同種メソッド
(TryDeleteDirectory等)も含めてPane.Testsへは切り出されていない(依存の無いクラスへの
切り出し対象はパス文字列の組み立てロジックそのものだが、Directory.CreateDirectory/
File.Copyと一体になっているため、今回は既存の設計方針(dotnet buildでの型検査+目視)を
踏襲し、新規テストは追加していない。

## 5. release.yml:43の式の直接展開

### 裏取り

`.github/workflows/release.yml:43`(修正前)`$tag = "${{ github.ref_name }}"`が、
GitHub Actionsの式展開をPowerShellの文字列リテラルへ直接埋め込んでいた。タグ名に
`"`・`` ` ``・`$()`のようなPowerShellのメタ文字が含まれていた場合、文字列の外へ
抜け出して任意のコードとして解釈されうる(式インジェクション)。トリガーは`v*`タグの
push のみで、タグを push できるのはリポジトリへ書き込み権限を持つ人に限られるため
実害は想定しにくい、という`docs/調査記録/点検-セキュリティ.md`の評価も含めて事実だった。

### 直した内容

`env: TAG_NAME: ${{ github.ref_name }}`を追加し、スクリプト側は`$tag = $env:TAG_NAME`
から読むように変更(定石どおりenv経由に変更)。以降のロジック(`-replace`・正規表現検証・
`$env:GITHUB_OUTPUT`書き込み)は変えていない。

### 検証

- `python3 -c "import yaml; yaml.safe_load(...)"`でYAML構文が壊れていないことを確認した。
- PowerShellの実行環境がこのコンテナに無いため、`$tag = $env:TAG_NAME`以降の
  スクリプト自体をローカルで実行して確かめることはできなかった(GitHub Actions上の
  windows-latestランナーでのみ実行される)。変更点は変数の参照元をリテラル埋め込みから
  環境変数に変えただけで、それ以外の行(`-replace`、正規表現、throw、GITHUB_OUTPUT書き込み)
  は一切変更していないため、既存のロジックへの影響は無いと判断した。
- **注意**: 実際に`v*`タグをpushしてこのワークフローを走らせる確認はしていない
  (指示どおり、リリースを壊さないよう変更を最小限に留めた。実際の動作確認は次のリリース
  タグpush時に行われる)。
