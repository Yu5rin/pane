## 前提調査: 仕様書10.2節と派生トークンの位置づけ

`docs/仕様書.md` 10.2節は基本6トークン(`--paper` `--ink` `--ink-mute` `--rule`
`--accent` `--accent-soft`)だけを表にしている。一方 `src/style.css` /
`src/themes.css` には既に `--menu-hover-fg` `--chrome-bg` `--sidebar-bg`
`--titlebar-bg` `--titlebar-fg` `--fold-guide-hover` 等の「派生トークン」が
存在し、いずれも次の作法で運用されている(`src/themes.css`冒頭のコメント参照):

- 新しい色そのものは導入しない。既存の6トークン(または`--ink-mute`等)から
  `color-mix()`または直接値で算出する
- 既定ライト・ダーク(`src/style.css`)に既定値を置き、9テーマすべて
  (2既定+`src/themes.css`の7プリセット)に**明示的に**定義する
  (問題ないテーマも「vars(--accent)のまま問題ない」という形で明示する)
- 各定義のコメントに実測コントラスト比と根拠を残す

今回もこの作法をそのまま踏襲した。**新しいCSS変数は2つだけ追加**
(`--accent-ink` と `--chrome-fg`)。CLAUDE.mdの「ここにない色・フォントを
新たに導入しない」は、新しい"色"(具体的な色相・パレット)を増やさないという
制約であり、既存トークンから算出した派生"トークン"を増やすこと自体は
`--menu-hover-fg`等の先例で既に許容されている、と解釈した。

## 直した内容

### 1. `--accent-ink`(文字用のアクセント色)を新設

`--accent`(仕様書10.2節の6トークンの1つ)は「アクセント面」用の中明度色で、
文字用の暗さ(明るさ)が保証されていない。直前の折りたたみマーカー修正
(`docs/調査記録/修正-折りたたみマーカー.md`)と同根の問題(ある用途向けにチューニングされた色を
別の用途に流用すると、テーマによってコントラストが保証されなくなる)。

`src/style.css`の`color: var(--accent)`(文字として使っている箇所)44箇所を
`color: var(--accent-ink)`に一括置換。あわせて、`var(--accent)`を背景にして
明るい文字(`--surface`/`--paper`)を乗せている6箇所
(`.btn.primary` `#btn-preview.on` `.ad-banner-action:hover`
`.extlink-btn-primary` `.pane-dialog-btn-primary` `mark.help-search-hit.current`)
は`background`/`border-color`を`var(--accent-ink)`に置き換えた
(コントラスト比はA vs BもB vs Aも同じ値なので、1つのトークンの実測で
「文字として使う」「背景にして明るい文字を乗せる」の両方向を保証できる)。

既定値は`var(--accent)`(既定ライト・ダークは実測で元々AAを満たすため無変更)。
`src/themes.css`側で4テーマ(sepia/solarized-light/solarized-dark/dracula)だけ
`color-mix()`で`--ink`(または白)へ寄せた値に上書きした。github/nord/nightは
`var(--accent)`のまま(実測で元々AAを満たす)を明示的に宣言。

### 2. `--chrome-fg`(ステータスバー等、chrome-bg上の文字色)を新設

`--ink-mute`は「本文(`--paper`)の上に乗る補助文字色」として調整された値。
`--chrome-bg`(メニュー・ステータスバー・タイトルバー用)は「本文より濃い
(暗い)」という別の設計方針の色のため、`--ink-mute`をそのまま乗せると
コントラストが保証されない。

`src/index.html`の`#statusbar`の`color`を`var(--ink-mute)`から
`var(--chrome-fg)`に変更。既定値は`var(--ink-mute)`(既定ダーク/github/nord/
dracula/dracula等は元々AAを満たす)。5テーマ(既定ライト・sepia・
solarized-light・solarized-dark・night)だけ`--ink`(または白)へ寄せた値に
上書き(既定ライトは`src/style.css`側に直接値、他4つは`src/themes.css`側で
`color-mix()`)。

### 3. 丸め誤差への対応(重要な学び)

理論値(Node.jsでのハンド計算、sRGBの単純な線形補間)でギリギリ4.5を超える
混合率(例: 5%, 20%, 34%等)を最初に選んだところ、実際のブラウザの
`color-mix()`の計算結果は微妙に異なり(丸め方の違いと思われる)、
`.verify-theme-ui.mjs`の実測で **4.49 や 4.51 のように4.5を僅かに割り込む/
ギリギリ超えるケースを複数検出した**(下記「実際に落ちたこと」参照)。
そのため、全ての新規混合率について「理論値が4.5をわずかに超える最小値」ではなく
「実測で4.7〜5.0程度の余裕を持つ値」を採用し直した(最終的な採用値は
`src/style.css`・`src/themes.css`の該当コメント参照)。

**教訓**: コントラスト比をcolor-mix()等で算出するときは、Node.js側の理論計算だけで
「4.5をわずかに超えた」と判断せず、必ず実ブラウザ(Playwright)の
`getComputedStyle`で実測し、かつ境界値ギリギリを狙わず余裕(0.2〜0.3程度)を
持たせること。

### 4. テスト側の副次的なバグ2件(このタスクの過程で発見・修正)

(a) `getComputedStyle().color`から`color-mix()`の解決結果を読むと、ブラウザに
よっては`rgb(...)`ではなく`color(srgb r g b)`形式(0〜1の値)で返ることがある。
`.verify-codefold.mjs` (Z)節や`.verify-theme-ui.mjs`の新設(G)節のコントラスト
計算関数(`relLum`)がこの形式を考慮していなかったため、`undefined`が返る
バグがあった → 両方に対応する正規表現を追加。

(b) `.verify-theme-ui.mjs` (G)節で、テーマ切り替え直後にDOM実測すると、
`body { transition: background .2s, color .2s; }`(`src/index.html`)の遷移
アニメーションが終わる前に読んでしまい、中間色を誤検出することがあった
(待ち時間120ms < 遷移時間200ms)。350msへ延長して解消。
