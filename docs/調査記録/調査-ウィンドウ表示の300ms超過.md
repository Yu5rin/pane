# 2枚目以降のウィンドウ表示が300msを超えていた件

結論: **超えていなかった。計測のしかたが間違っていた。**

## 何が起きていたか

実機ログ(2026-09-05)で、ウィンドウを開くたびに次の警告が出ていた。

```
[警告] 遅い処理: 2枚目のウィンドウの表示 が 302ms かかった (閾値300ms)
[警告] 遅い処理: 6枚目のウィンドウの表示 が 357ms かかった (閾値300ms)
```

仕様書8.4節「既存インスタンスへのファイル追加表示 300ms以内」に対する未達に見えた。

## 何が違ったか

`PaneApplicationContext.OpenWindow` の計測が、こうなっていた。

```csharp
long afterBytes = MeasureTotalMemoryBytes(out bool ownOnly);  // 重い
...
Logger.Write($"...表示まで{stopwatch.ElapsedMilliseconds}ms...");  // 計測の「あと」に読む
```

`MeasureTotalMemoryBytes` は、WebView2の各プロセスを `Process.GetProcessById` で開いて
`WorkingSet64` を足す。ウィンドウが増えればプロセスも増えるので、この処理自体が重くなる。
その所要時間が「表示までの時間」に足し込まれていた。

ログの時刻から実際の時間(MainForm生成 → WebView2を表示)を引き直すと、こうなる。

| | 報告値 | 実際 | 差(=メモリ計測の時間) |
|---|---|---|---|
| 2枚目 | 302ms | 246ms | 56ms |
| 3枚目 | 319ms | 258ms | 61ms |
| 4枚目 | 333ms | 251ms | 82ms |
| 5枚目 | 335ms | 256ms | 79ms |
| 6枚目 | 357ms | 278ms | 79ms |

**すべて300ms以内だった。**

**兆候はログに出ていた。** 報告値が枚数とともに単調に伸びる一方、JS側の描画時間
(147→184ms)はそれほど伸びていない。数えるプロセスが増えていたのだから当然だが、
「枚数が増えると遅くなるものだ」と受け流していた。

## どう直したか

測り終えた時刻を、他のことをする前に確定させる。あわせて、メモリ計測自体に
何msかかったかもログへ添えた(同じ誤解を繰り返さないため)。

```csharp
long elapsedMs = stopwatch.ElapsedMilliseconds;   // 先に確定させる
long afterBytes = MeasureTotalMemoryBytes(...);   // そのあとで測る
```

## 直したあとの実測（2026-09-06）

警告は0件になり、17枚まで開いても表示は239〜287msだった。目標の300msは元から
満たしていた。

同時に、**計測そのものが重くなり続けていること**が見えた。

| ウィンドウ | 表示まで | メモリ計測にかかった時間 |
|---|---|---|
| 2枚目 | 287ms | 53ms |
| 8枚目 | 239ms | 102ms |
| 12枚目 | 254ms | 134ms |
| 17枚目 | 268ms | 157ms |

ウィンドウが増えるほど数えるプロセスも増えるので当然だが、これはUIスレッドの上で、
しかも**ウィンドウを開く前と後の2回**走っていた。製品の動作には要らない処理で
毎回UIを止めていたことになる。

仕様書8.4節の目標は「2枚目以降のウィンドウ」であって、17枚目を測る必要はない。
最初の数枚（2〜5枚目）で打ち切るようにした（`MeasuredWindowLimit`）。

**計測を足すときは、その計測自体のコストも見る。** 今回は2つとも同じ処
（計測が実態を歪める・計測が実害を出す）から出ている。

## メモリの60MB目標（決着）

内訳を採った結果（実機ログ 2026-09-06）。

```
2枚目を開く前: Renderer×3=231MB, Browser×1=147MB, Gpu×1=78MB, Utility×2=59MB
2枚目のあと:   Renderer×4=315MB  (+84MB)
3枚目のあと:   Renderer×5=416MB  (+92MB)
4枚目のあと:   Renderer×6=513MB  (+97MB)
5枚目のあと:   Renderer×7=612MB  (+92MB)
```

**増えるのは描画プロセス（Renderer）だけで、1枚あたり84〜97MB。**
Browser（147→160MB）・Gpu（78→82MB）・Utility（59MB固定）は枚数によらずほぼ一定だった。

つまり、**60MBは達成できない数字だった**。CodeMirrorと本文を載せたChromiumの描画
プロセスとして84〜97MBは妥当な大きさで、Pane側で削れる余地はほとんどない。
仕様書8.4節の目標を110MB以内へ改めた。

### 仕様書8.1節の説明も正確ではなかった

> 別プロセスで起動するとウィンドウごとにブラウザプロセス一式が立ち上がり、
> 1枚あたり100MB超が加算される

同一プロセスでも描画プロセスは分かれるので、100MB超は同じだけ増える。1プロセスに
保つことで節約できているのは Browser + Gpu + Utility の約290MB分（これがウィンドウごとに
増えるのを防いでいる）だった。**プロセス設計の判断自体は正しく、説明が不正確だった**ため、
実測に合わせて書き直した。

### 2枚目を開く時点で既に描画プロセスが3つある

本体ウィンドウ + 設定ウィンドウの事前生成 + 取扱説明書ウィンドウの事前生成である。
起動直後から、まだ開いてもいない2つの画面が描画プロセスを1つずつ持っている（約160MB）。

速度と引き換えの設計で、実際に設定画面は35msで開くようになっている（それ以前は8.5秒）。
ただしメモリの代価は見えていなかったため、設定「設定と取扱説明書の画面をあらかじめ
用意しておく」（仕様書 C-15、既定オン）で切れるようにした。

## 事前生成を切ってみた結果（2026-09-06）

設定 C-15 をオフにして実機で確かめたところ、**2つ分かった**。

### 1. 入口を1つしか塞いでいなかった

```
13:11:52.564 [詳細] 事前生成: 設定で無効になっているため行わない
...
13:12:00.805 HelpWindow: 事前生成(Prewarm)開始     ← 走ってしまっている
```

事前生成には2つの経路がある。

- 本体ウィンドウが使える状態になったとき（`SchedulePregenerationAfterFirstWindow`）
- コンストラクタで始まるタイマー（上が来なかったときの保険。preload起動では常にこちら）

判定を前者にだけ置いていたため、後者が素通りしていた。
**入口が複数あるものは、入口ごとではなく実行する側で塞ぐ。**
`PregenerateSettingsWindow` / `PregenerateHelpWindow` の冒頭へ移し、あわせて
コンストラクタでもオフならタイマー自体を回さないようにした。

### 2. 「オフにすると数秒待つ」は誤りだった

実測は **35ms（オン）→ 134ms（オフ）** で、差は100ms程度だった。

そう書いてしまったのは、この設定を足す前の「設定画面の初回表示が8.5秒」という
数字を引きずっていたため。その8.5秒はv1.1.5の `Program.WarmUpForSettingsWindow`
（フォント列挙とPandoc検出を起動直後に済ませる）で既に解消しており、事前生成が
無くても重い部分は終わっている。事前生成が省いているのはWebView2の生成と描画だけで、
それが100ms。

**また実測を持たないまま数字を書いた。** 設定の説明文・ツールチップ・仕様書C-15・
ソースのコメントをすべて実測値へ直した。

## 2枚目のウィンドウだけ300msに近い

3〜5枚目が249/298/280msなのに対し、2枚目は287ms（9/5）・311ms（9/6）と、300msを挟んで
ばらついている。2枚目のときにWebView2の描画プロセスを新規に起こすためで、目標を割って
いるわけではないが余裕はない。今のところ実害は無いため手を入れていない。
