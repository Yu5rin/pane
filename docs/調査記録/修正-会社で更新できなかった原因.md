# 会社のPCで一度も更新できなかった原因は、GitHub APIの問い合わせ上限だった

対応した版: v1.1.7

前回（`修正-更新の失敗を追えるようにする.md`）で「原因が分かるまで手を入れない。
ここまでは分かるようにするための変更だけ」と書いた。その仕込みを入れた v1.1.6 を
会社のPCで動かしてもらい、ログが採れた。

## ログに出ていたもの

```
13:33:13.891 [警告] 更新の確認: 問い合わせ回数の上限に達していた(403)
13:33:13.891 更新の確認: 新しい版(v1.1.6)はあるが、配布物の詳細を取れなかった。手動更新を案内する
```

**プロキシでもSSL検査でもなかった。** ダウンロードは一度も始まっていなかった。
その手前、配布物のURLを調べる段階で止まっていた。

GitHubのAPIには1時間60回（未認証）の上限があり、**IPアドレスごとに**数えられる。
会社のように多数のPCが同じ出口IPを共有している環境では、他の通信で先に使い切られる。
自宅は専有IPなので上限に当たらない。

- 「会社では1回も成功しない」→ 常に上限に達している
- 「自宅では必ず成功する」→ 一度も上限に当たらない

報告そのままの形をしていた。

## なぜ確認だけは通っていたのか

普段の確認はAtomフィード（`releases.atom`）で行っている。**Atomは上限とは別枠**
なので、会社でも「新しい版がある」ことまでは分かっていた。上限に当たるのは、
そのあと配布物の詳細（ダウンロードURLとSHA256）を取りに行くAPIのほうだけだった。

「確認はできるがダウンロードできない」という報告は、正確には
「確認はできるが、**ダウンロード先が分からない**」だった。

## 直したこと

### 1. ダウンロードURLをAPIに頼らず組み立てる

配布物のURLは規則で決まっている。

```
https://github.com/{owner}/{repo}/releases/download/{tag}/Pane-{tag}-win-x64.zip
```

タグはAtomから分かる。ownerとrepoは設定の `updateCheckUrl` から分かる。
APIを使わずに求められる（`UpdateCheckLogic.TryBuildDownloadUrl`、テスト5件）。

引き換えにSHA256は取れない（APIからしか出てこない）。照合を省いて続行する経路は
元からあり（`VerifyHash` は空なら警告を出して続ける）、HTTPSで取得している以上
そこで防げるのは転送中の破損だけ、という点も変わらない（README・取扱説明書・
仕様書U-03に明記済み）。**上限に当たっている限り一度も更新できない**ことのほうが
実害が大きい、と判断した。

この組み立ては、ファイル名の付け方が `scripts/release.ps1`（`Pane-v$Version-$Rid`）と
一致していることを前提にしている。将来ワークフロー側で名前を変えるなら、
`BuildAssetFileName` も直す必要がある。組み立てたURLが404なら、ダウンロードに
失敗するだけで誤ったものは入らない。

### 2. 「通信を確かめる」が、まさに最新版のときに動いていなかった

同じログに、こう出ていた。

```
[警告] 更新の通信確認: 配布物のURLが分からなかった(status=latest, ...)
```

`CheckConnectionAsync` は `CheckAsync` の結果から `DownloadUrl` を取っていた。
ところが最新版のとき `CheckAsync` は `latest` を返し、配布物の詳細を取りに行かない。
`DownloadUrl` は空のままになる。

前回の記録に「**最新版でも何度でも押せることが要点**」と書いた、まさにその場合に
動かないものを作っていた。要点だと自分で書いたことを、実装で満たしていなかった。

確かめたいのは「配布物の置き場まで通信が届くか」であって、更新の要否ではない。
URLが空なら、いま分かっているタグから組み立てるようにした（1と同じ仕組み）。

## 会社のPCは全体に遅い（これは別件）

同じログから、自宅との差が出ていた。

| | 会社 | 自宅 |
|---|---|---|
| バンドルの評価 | 2100ms | 60ms前後 |
| WebView2 | 138 | 152 |
| フォント | 319件 | 746件 |

更新の失敗とは関係がない（更新は接続の前段で止まっていた）。別に見る。

## 繰り返さないために

- **「上限に達した」で終わらせない。** 上限に当たるのが常態の環境がある。
  そこでは「しばらく待てば直る」は成り立たない
- **手元で必ず成功することは、どこでも成功することを意味しない。** 自宅の専有IPでは
  この問題は永久に再現しない。「家では動く」は反証にならない
- **要点だと書いたことを実装が満たしているか、その経路で確かめる。**
  U-08は「最新版でも押せること」が存在理由なのに、最新版で動かなかった。
  `修正-貼り付けで改行が増える.md` の「入口が複数あるものは実行する側で塞ぐ」と
  同じ形の抜けで、書いた直後にまた作っている
