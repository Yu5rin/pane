## 「開く」で空の無題ウィンドウが残るか(未確定1件、実際に問題ありと確認して修正)

`Pane/PaneApplicationContext.OpenWindow`自体には確かに再利用処理は無いが、
`Pane/MainForm.cs`の`HandleOpenRequest`(File > 開くダイアログ)を読んだところ、
ダイアログで選んだ結果を**無条件に**`_requestNewWindow?.Invoke(...)`していた
(= 常に新しいウィンドウを作る)ため、**実際に問題があった**と確認できた:
起動直後の空の無題ウィンドウでCtrl+Oしてファイルを選ぶと、新しいウィンドウが開き、
元の空ウィンドウは使われないまま残る。

一方、比較対象の`openFolder()`(src/main.js)・D&D(`OpenDroppedPathAsync`、Pane/MainForm.cs)は
どちらも「本文が空(失うものが無い)なら現在のウィンドウで開き、何か書かれていれば新しいウィンドウで
開く」という基準(`RequestIsDocumentEmptyAsync`によるJSとの往復判定)で統一されており、
**「開く」ダイアログだけがこの基準から取り残されていた**。コメントにあった「新規作成・開くは
常に別ウィンドウ」という過去の決定は、Ctrl+N/Ctrl+Shift+N問題(H5)の文脈での「ウィンドウの
内容を無警告で失わせない」ためのものであり、失うものが無い空ウィンドウにまで新しいウィンドウを
強いる理由にはならないと判断し、**実際に修正した**。

### 直した内容(Pane/MainForm.cs)
- `HandleOpenRequest()`(void)→`HandleOpenRequestAsync()`(Task)に変更。
  ダイアログでファイルを選んだあと、タブ形式なら新しいタブへ、そうでなければ
  `RequestIsDocumentEmptyAsync()`で本文が空かを問い合わせ、空なら`OpenFile(path)`で
  現在のウィンドウへ読み込み、空でなければ従来どおり`_requestNewWindow`で新しいウィンドウへ。
- 呼び出し元(`case "open":`)を`_ = HandleOpenRequestAsync();`に変更(`case "open-path":`等、
  既存の非同期ハンドラと同じ「送りっぱなし」の作法)。
- サイドバー右クリック「新しいウィンドウで開く」(`open-path-new-window`)は明示的に
  新しいウィンドウを選んだ操作のため**空文書判定は入れず**、従来どおり常に新しいウィンドウ
  (コメントを更新し、旧メソッド名`HandleOpenRequest`への参照も直した)。

### 検証・制約
- `npm run build`・`dotnet build`・`dotnet test`(172件)はすべて通過。
- **この変更はC#のWinFormsダイアログ(`OpenFileDialog`)を実際に開いて確認する必要があり、
  この環境(Linuxコンテナ、ヘッドレス)ではPlaywrightのJS検証もdotnet testも
  この分岐を自動では検証できない。** ロジック自体はD&D側(`OpenDroppedPathAsync`)と
  ほぼ同一の既存パターンを踏襲しているため既存の`.verify-*.mjs`で間接的な信頼はできるが、
  **Windows実機で「空の無題ウィンドウでCtrl+O→現在のウィンドウに読み込まれる」
